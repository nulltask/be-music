# 0040: スクラッチのホールドを記録した入力ソースで識別する

ステータス: 承認済み。日付: 2026-11-06。[ADR 0037](./0037-scratch-spin-input.ja.md) の判定に関する部分を置き換えます。

## 背景

beatoraja はスクラッチのロングノートを始めた物理キーを覚え（`JudgeManager` の `sckey`、[`83574048`](https://github.com/exch-bms2/beatoraja/blob/83574048ba489082eb46df7fe9806b464bf1f526/src/bms/player/beatoraja/play/JudgeManager.java#L351-L370)）、それで 3 つの規則を決めます。別のキーの押下はバックスピンスクラッチ（BSS）を終えて終点を判定します。始めたキーの離鍵は、`POOR` になるときだけ BSS を終えます（[L494-L511](https://github.com/exch-bms2/beatoraja/blob/83574048ba489082eb46df7fe9806b464bf1f526/src/bms/player/beatoraja/play/JudgeManager.java#L494-L511)）。スクラッチの LN は始めたキーでしか離せません（[L522-L531](https://github.com/exch-bms2/beatoraja/blob/83574048ba489082eb46df7fe9806b464bf1f526/src/bms/player/beatoraja/play/JudgeManager.java#L522-L531)）。ADR 0037 は BSS を記録した回転方向（`'cw'` / `'ccw'`）で判定していました。2 キーのスクラッチでは 1 つ目の規則を再現できますが、残りの 2 つは再現できず、同じ向きに回す 2 つのキーを区別できません。

オーナーは issue #605 で、ターンテーブルの回転方向、キーボードのキー、コントローラーのボタンがひとつの入力ソースのモデルを共有すること（PHENIXWAN のような専用コントローラーを見据えたもの）、リプレイにデバイスを識別するデータを記録しないこと、リプレイ形式に後方互換は不要であること（まだリビジョン 0）を決めました。

判定コア、リプレイ、リプレイシミュレーターは、同じ記録入力から同じ判定に至らなければなりません。そのためソースは入力の一部である必要があります。検討した案は次のとおりです。

1. **回転方向を残し、離鍵の規則を上乗せする。** 回転方向は向きであって識別子ではありません。同じスクラッチレーンで同じ向きに回す 2 つのキーを区別できず、スクラッチ LN の規則にはキーそのものが必要です。
2. **生のキートークンを記録して正本にする。** トークンはホストごとの綴りで（`'ctrl-left'` と `'control-left'` は同じキー）、タッチレーンはキーボードのキーのトークンを使い回し、コントローラーにはトークンがありません。
3. **リプレイごとのソースの表を、すべての入力から参照する。** `play.inputSources` が物理的な入力をひとつずつ（`kind`、大まかな `device`、正規化した `label`、ターンテーブルの `direction`）並べ、どの入力イベントも `source` でそのひとつを指します。

## 決定

案 3 を採ります。すべての `ReplayInputEvent` は `play.inputSources` を指す必須の整数 `source` を持ちます。`tokens` は廃止し、`spin` は表示用にだけ残します。`parseReplay` は id の一意性、参照が解決すること、`direction` がちょうどターンテーブルのソースにあることを検査し、ソースのないログは推測せずに拒否します。`play.analogScratch` は、ホストがアナログ軸を押下に変えたアルゴリズムを任意で記録します。ログには変換後のイベントを残し、軸のサンプルは残しません。

レーンに割り当てた物理キーはそれぞれ独立したソースです（`keyboardInputSource`、最初のトークンで名付けます）。各レーンのタッチ領域はひとつのソースで、コントローラーは入力コマンドでソースを渡します。Gamepad API の入力はまだありません。`lane-input` と `kitty-state` コマンドの `source` フィールドが、コントローラーのホストが接続する境界です。

判定コアとシミュレーターは、スクラッチのホールドで始点のソースを覚えます。別のソースの押下は、BSS を演奏するすべてのルールセット（beatoraja の CN / HCN と、名前を言ってはいけないあのゲームのすべてのロングノート）で BSS を終えます。beatoraja だけ（`RulesetConfig.scratchHoldsBySource`）は、始点のソースの離鍵が `POOR` になるときにその場で BSS を終え、スクラッチ LN は始点のソースでしか離せません。LR2 は変わりません。

**ソースがひとつのレーンは緩い規則で演奏します。** 厳密な規則では、ソースがひとつのレーンのどの BSS も終えられません。対になるソースがあるかはソースの性質です（`hasScratchCounterpart`）。ターンテーブルの回転方向には常に逆方向があり、キーボードのスクラッチレーンには少なくとも 2 つのキーがあるので、どちらも厳密な規則です。タッチの領域、コントローラーのボタン、不明なソースは緩い規則で、レーンへの新たな押下が BSS を終え、離鍵は何も確定しません。割り当てではなくソースから決めるので、リプレイだけから分かり、ライブのプレイと再シミュレーションは常に一致します。

## 結果

この変更より前に記録したリプレイはもう読み込めず、Leaderboard は `invalid-replay` として拒否します。Leaderboard に保存済みのリプレイも読み直せなくなります（プレイしたファイルの補完では長さを持ちません）。beatoraja の規則が効くところではスコアが変わります。終点よりずっと前に離した BSS は `POOR` になり、スクラッチ LN は別のキーの離鍵では離れません。レーンのホールドと ANY KEY の割り当てはソースで識別するので、ライブのエンジンとそのリプレイは同じように識別します。コントローラーのホストはソースを名付けるだけで済みます。コントローラーのボタンひとつだけを割り当てたレーンは緩い規則になりますが、将来の割り当て表で厳密にできます。大まかな `device` の種別があれば、データを増やさずに、後からキーボードとコントローラーのランキングを分けられます。
