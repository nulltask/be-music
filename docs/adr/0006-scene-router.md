# The host routes every scene transition through one scene router

In the web player one **scene router** owns the current scene. It mounts the next scene as the current one exits, then disposes of the scene that left. It retains the select scene across decide, play and result. The router saves an active video before changing scenes. When the recording includes a result, it mounts the result first and keeps the play's audio graph until the file is saved. Transitions are serialized, and a scene built for a navigation that a newer one replaced is disposed instead of shown, so a late asynchronous step cannot land on a newer scene. A navigation the scenes did not ask for (a drop, a skin or theme change, files loaded) interrupts the run they lead through, and the host ends it as that navigation begins. Course runs, records and replays, the library, settings, the Options dialog and themes are separate modules that the app's composition root (`app/app.ts`) only wires together; `main.ts` only boots it. The 5,600-line host disposed a different set of views on each path: a drop or a skin change during a play lost the recording and left a course run active, so the next single play counted as a stage, and F5 dropped AUTO and replay.
