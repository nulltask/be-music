# Historical BMS dialect commands

[日本語](./historical-bms-commands.ja.md)

This note classifies the historical dialect commands listed in [#837](https://github.com/nulltask/be-music/issues/837) by origin, player support and actual use, and records what Be-Music does with each. It is the basis for the "Partially supported and unsupported commands" table in the [player specification](../player-spec.md#partially-supported-and-unsupported-commands).

## Sources

- Command descriptions, origin and support lists: hitkey's [BMS command memo](https://hitkey.nekokan.dyndns.info/cmds.htm) (the live host was unreachable on 2026-10-31; read through the [Web Archive copy](https://web.archive.org/web/2024/https://hitkey.nekokan.dyndns.info/cmds.htm)). Anchors are given per command below.
- Be-Music behavior: `packages/chart-parser/src/core/bms-headers.ts` (`pushHeaderLine`) and `packages/chart-writer/src/bms.ts`.
- Usage: a line-start scan of the local test corpus. It holds **5,344 BMS-family files (5,142 unique by SHA-256)**: the BMS Starter Pack and gdbg packages 2022–2025 used in earlier #822 counts (2,720 files), plus other artist and event collections. bmson files are not relevant here. Charts are not committed.

## Current parser behavior

Apart from `#EXBPMxx` (see Follow-ups), none of the commands below has a dedicated parser branch. A non-empty value falls into the default case of `pushHeaderLine` and is kept verbatim in `metadata.extras` under its uppercased command (`#ExtChr` becomes `EXTCHR`). The BMS writer writes `metadata.extras` back as header lines, so they survive BMS and Be-Music JSON round trips. No player, renderer or fingerprint reads them. `#MATERIALS`, `#DIVIDEPROP` and `#VIDEOFILE` have their own `bms` fields with the same "kept, not executed" status.

## Follow-ups

- `#EXBPMxx` (done): the parser rewrites it to `#BPMxx` on input, as it does for the control-flow spellings. File order, branches, fingerprints and output therefore treat both as one definition, and the later line for one index wins. Legacy Be-Music JSON that kept it in `metadata.extras` migrates into `resources.bpm` unless `#BPMxx` defines the index. See [format compatibility](../format-compat.md).

## `#MIDIFILE` and `#VIDEOFILE` (#836)

| Command                         | Origin → support (cmds)                                                            | LR2 / beatoraja                                    | Corpus use | Decision    |
| ------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------- | ---------- | ----------- |
| `#MIDIFILE` ([`MIDIFILE`][d])   | BM98 → BM98, BMSV, DDR, RDM, IIDXv, HDX; cmds: hardware-dependent, not recommended | Not supported [C] / not supported [V]              | 0 / 5,344  | Unsupported |
| `#VIDEOFILE` ([`VIDEOFILE`][f]) | bemaniaDX → bemaniaDX (with `#VIDEOf/s`, `#VIDEODLY`, `#VIDEOCOLORS`)              | Not supported; video goes through `#BMPxx` [C] [V] | 0 / 5,344  | Unsupported |

Be-Music follows LR2 outside the ruleset and beatoraja where LR2 has no behavior; neither player executes these commands, and video BGA already works through `#BMPxx`, which LR and both reference players use. A MIDI path would also need a bundled synthesizer and instrument set whose sound the chart cannot specify, the same hardware dependence cmds warns about. With no use in the corpus, neither cost is justified. Both values stay in `bms.midiFile` / `bms.videoFile`, and `#VIDEOf/s` / `#VIDEODLY` in `metadata.extras`, for lossless round trips; a chart that relies on them plays without that BGM or video. Reopening this needs a chart that uses them and an issue of its own.

Everything else stays unsupported. It is kept in `metadata.extras` for lossless round trips, with no runtime meaning.
