# LR2 の 14 KEY におけるスクラッチ同時刻の鍵盤回避

[#1076](https://github.com/nulltask/be-music/issues/1076) は、14 KEY の S-RANDOM と CONVERGE で、スクラッチと鍵盤が同時刻にあるときの配置を扱います。

## LR2 beta3 の挙動

- LR2 は配置を決める前にオブジェクト配列全体を実時刻で並べ替えます。比較関数は時刻だけを使います。それ以前の BMS 時刻による並べ替えでは同時刻をオブジェクトコードで比較しますが、後の並べ替えで同時刻の順序が変わり得ます。実時刻の並べ替えにスクラッチが先に入っても、鍵盤が先に配置されることがあります。[OpenLR2 の最初の並べ替え](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L26397) · [実時刻の並べ替え](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L27065) · [比較関数](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L23975-L24011)
- 14 KEY の配置処理がスクラッチオブジェクトに達すると、1P は鍵盤 4〜7、2P は鍵盤 1〜4 に回避の印を付けます。その側・その行の後続の抽選に効き、同じ行ですでに配置した鍵盤の行き先はそのままです。スクラッチによる印付けは 14 KEY で実行されます。[OpenLR2 の印付け](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L27404-L27424)
- S-RANDOM と CONVERGE は、同時刻のオブジェクトや保持中のロングノートが占有する行き先を除外します。ほかの条件を満たす行き先でも、印の付いた鍵盤を受け入れるのは抽選範囲内の全候補に印が付いたときです。この判定では印と占有状態を別々に見ます。近い鍵盤がロングノートで占有され、印が付いていない場合は、空いている遠い鍵盤も拒否され続けることがあります。CONVERGE は最初に固定キーを試し、同じ条件で受け入れを判断します。[OpenLR2 の抽選と再抽選](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L27367-L27405)

OpenLR2 は入力時刻が進んだときに側ごとの印を消します。このときは DP FLIP 前のオブジェクトコードを使い、スクラッチへの印付けにはレーン変換後のコードを使います。[OpenLR2 の印のリセットと DP FLIP](https://github.com/GOMazk/OpenLR2/blob/583a38503555e59c4bafa49d60b9d0714c9007c2/LR2f.cpp#L27274-L27321)

## 実行ファイルでの検証

手元の LR2 beta3 100201 の `LR2body.exe` の SHA-256 は `a46ef15343e41d3411771c83ac7b0c42d95e5f473db69c6b45a9584c07e94480` です。合成したオブジェクトを入力し、実行ファイルの 32 ビットコードを Unicorn で実行しました。対象は `0x4b418d–0x4b4196` から呼ばれる並べ替え `0x717f80` と比較関数 `0x4ac2b0`、配置と印付けの `0x4b4cd1–0x4b4e7f` です。配置の検証では乱数関数 `0x6c95e0` に決めた値を返させました。Windows アプリの起動と BMS パーサーを通した譜面の読み込みは未検証です。

| 検証                                                                     | 結果                                                                       |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 同時刻の 1P スクラッチ、鍵盤 1 の順で並べ替えに入力                      | 鍵盤 1 が先                                                                |
| 同じ組に前後 4 オブジェクトずつ追加                                      | スクラッチが先                                                             |
| 同時刻の 2P スクラッチ、鍵盤 1 の順で並べ替えに入力                      | 鍵盤 1 が先                                                                |
| 14 KEY で鍵盤を先に処理                                                  | S-RANDOM は遠い鍵盤を採用。CONVERGE も遠い固定先を採用。                   |
| 14 KEY でスクラッチを先に処理                                            | 両側とも S-RANDOM と CONVERGE は遠い行き先を拒否し、次の近い行き先を採用。 |
| 10 KEY のフラグでスクラッチを先に処理                                    | スクラッチによる印付けは発生しない。                                       |
| 14 KEY で 1P スクラッチが先、近い 3 鍵はすべて印付き                     | 空いている遠い鍵盤を採用。                                                 |
| 14 KEY で 1P スクラッチが先、鍵盤 2・3 は印付き、鍵盤 1 は印なしで保持中 | 遠い鍵盤は拒否され続け、検証側の抽選上限で終了。                           |

並べ替えの検証では、組の時刻を 1000、前の 4 オブジェクトを 100・110・120・130、後ろの 4 オブジェクトを 1100・1200・1300・1400 に設定しました。配置の検証では 1P に鍵盤 5、次に鍵盤 1、2P に鍵盤 2、次に鍵盤 5 を与えました。CONVERGE は対応する遠い行き先を最初に試す設定です。DP FLIP を使わない条件で、各処理を単独で確認しました。

## AC と PC 版の挙動

コナミの AC 版マニュアルでは、S-RANDOM は音符ごとに配置を変え、スクラッチは移動しないと説明しています。INFINITAS のマニュアルは H-RANDOM が S-RANDOM に依存することを説明しています。ダブルプレーでスクラッチと同時刻の鍵盤の抽選が変わるかどうかは記載されておらず、AC と PC 版の回避条件は未確認です。[AC 版オプションマニュアル](https://p.eagate.573.jp/game/2dx/26/howto/play/option.html) · [INFINITAS オプションマニュアル](https://p.eagate.573.jp/game/infinitas/2/howto/option.html)

## Be-Music での実装判断

Be-Music は解決済みの譜面と小節レコード、BGM・BGA・BPM・STOP などから並べ替えの入力を組み立て、LR2 beta3 の実時刻の並べ替えと配置時の再抽選を再現します。BMS からの回帰テストで 14 KEY の両側と両方の処理順を、10 KEY の対照テストで従来の配置を確認しました。LR2 実行ファイルとの比較は並べ替えと配置ルーチン単体で行いました。LR2 のローダー全体との一致は未検証です。bmson には Be-Music の解決済みオブジェクトを使います。

AC 判定ルールの共有 S-RANDOM は従来の配置を使います。選べるレーンがない場合や 1,024 回の試行で決まらない場合は譜面準備をエラーにします。既存リプレイは記録済みの配置を使います。
