Add the Be-Music Fingerprint (`bmfp1`, see docs/fingerprint-spec.md), which identifies a chart by what the player plays and sees in the lanes rather than by its bytes: `computeChartFingerprint` identifies a chart file with its `#RANDOM` / `#SWITCH` outcomes kept as decision trees, `computePlayFingerprint` hashes the chart after its branches were chosen to identify one play, and `createChartFingerprintDocument` / `createPlayFingerprintDocument` / `canonicalizeFingerprintDocument` expose the canonical document behind them. Charts that differ only in BGA, BGM, keysounds, metadata, line order, `#WAV` numbering, measure resolution, decimal precision, or BMS against bmson (when every position is exact at the bmson resolution) share a fingerprint, while anything the engine plays differently changes it: positions and long-note ends are exact, only decimal values snap to small-denominator rationals within a stable tolerance, SPEED is modelled as the engine interpolates it, STOPs of one time add up, and engine fallbacks (`#TOTAL`, `#RANK`, `#BASEBPM`, FREE ZONE, bmson defaults) normalize alike. Control flow follows the parser's single-stack semantics, so definitions made in a branch apply to the whole chart, a missing `#ENDIF` behaves as in the parser, and `#ELSE` / `#SWITCH` writings that play alike share a fingerprint; a factor over the evaluation budget gets a deterministic opaque node instead of hanging. The lane-mode input (the chart path or extension, read with `resolveChartPlayVariant`'s `.pms` / `.bme` rules) is a required option. Both fingerprint functions return the `bmfp1:` string synchronously, hashing with a small built-in SHA-256 instead of Web Crypto, so synchronous callers can use them in Node and browsers alike.
