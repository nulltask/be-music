# ゴールデンコーパス

`corpus.test.ts` は [`examples/test`](../../examples/test/README.ja.md) のすべての譜面をツールチェーン全体に通し、各段階の出力を `__golden__/<譜面名>.json` に固定します。ユニットテストは「関数がどう振る舞うべきか」を検証します。このスイートは「実際の譜面ファイルに対して、ツールチェーンが今どう振る舞っているか」を記録します。そのため、パッケージをまたいでロジックを移すリファクタで、どこかの段階の出力が変わった時点でここが失敗します。

## 各ゴールデンファイルの内容

- `parse`: メタデータ、リソース、小節、BMS / bmson 拡張、制御構文のディレクティブ、全イベント（`小節:チャンネル@分子/分母=値`）。
- `stringify`: 元の形式に書き戻した譜面（1 行ごとに配列の 1 要素）と `roundTripPlayableNotesEqual`。後者は、出力を再度解析したときに同じ演奏ノーツが得られるかどうかです。
- `variants`: `#RANDOM` の引き方ごとに 1 項目あります（制御構文がある譜面は `random-low` / `random-high`、ない譜面は `default`）。各項目には次の内容が入ります。
  - 引いたパターン、プレイ形態、基準 BPM
  - テンポと STOP の点
  - すべての発音トリガー
  - playlog の譜面情報
  - engine がプレイ用に準備したノーツ列
  - 3 種類の固定入力に対する LR2 / beatoraja / IIDX シミュレータの結果。入力は `missed`（入力なし）、`perfect`（全ノーツをジャストで押す）、`offset`（押すタイミングを全判定窓に散らし、7 ノーツに 1 つは押さない）の 3 つです

時刻は整数のマイクロ秒、拍は 1e-6 に丸めているので、浮動小数点の誤差は差分として出ません。

## 実行と更新

```bash
pnpm test:golden
```

```bash
pnpm test:golden -u
```

ゴールデンの差分が出ても、それがすぐバグを意味するわけではありません。意図した変更なら `-u` で再生成し、プルリクエストでコードと同じように差分をレビューしてください。`examples/test` に譜面を追加すると、ゴールデンファイルも自動で追加されます。

## engine のプレイ結果を固定していない理由

engine は各 variant につき入力なしで 1 回だけ動かし、準備したノーツ列を取り出すためだけに使います。プレイ結果は純粋関数であるルールセットシミュレータで求めます。engine は実時間の tick ループで判定するため、リプレイ結果が実行ごと・再生速度ごとにまだ変わります（上限 100 % で頭打ちになるゲージの適用順や、ループ終了後に残った離鍵が落ちることなど）。これを固定するとこのスイートが不安定になります。engine とシミュレータが一致するかは、`packages/player/src/playlog/equivalence.test.ts` が厳選したケースで検証しています。
